Yes. I’d pause before using this with real tenant data. The model, authentication, and admin layers have several important gaps:

Critical: development settings remain in source. settings.py contains a development SECRET_KEY and DEBUG is enabled. Keep production secrets out of source, configure them through the deployment environment, and disable DEBUG in production.

Critical: the custom user manager is not a Django manager. models.py:107 declares CustomUserManager without inheriting from BaseUserManager, yet its methods call manager-provided attributes such as normalize_email, model, _db, and filter. In particular, create_user cannot work as written, which breaks a standard account-provisioning path and likely createsuperuser. Make it a proper BaseUserManager subclass and test create-user, create-superuser, and tenant query methods.

High: a user’s role is not checked against their university. User.role accepts any role, and models.py:233 validates staff status and school affiliation but not role ownership. Meanwhile, models.py:219 trusts the assigned role’s permission list. The admin dropdown’s tenant filter is not enough: other code can save a user with another university’s role, and User.save() does not reject it. Enforce that a role is global or belongs to the user’s university in a shared model/service validation path.

High: the role migration can silently change existing authority. 0002_permission_hierarchy_and_schools.py:38 adds level with default 4; 0003_remove_role_role_type_alter_role_level.py:13 removes role_type without mapping existing values. Existing university admins may therefore become level-4 roles, and the original schema used department_admin, not school_admin. Add a data migration mapping old role values to intended levels, audit the resulting users and permissions, and verify it on a production-like database before applying.

High: disabling an account does not reliably end its existing session. Login checks is_active, but backends.py:26 returns the user without checking it. The permission decorators also check is_authenticated and role permissions, not is_active (decorators.py:13, decorators.py:32). A user disabled after login can remain authenticated for decorated non-admin views. Reject inactive users when restoring sessions and centralize the active-user check across middleware and decorators.

High: school boundaries are only partially enforced. The level-3 school requirement is in admin form validation, not models.py:233, so non-admin model writes can create a school-admin user without a school. Also, school-admin users are filtered to their school in the user admin, but admin.py:322 is university-wide, and the role queryset is also tenant-wide. A school admin can see schools and subordinate roles outside their own school, and may manage them if granted those permissions. Put the level-3 school invariant in model/service validation and apply school scope consistently to school and role administration.

The project now targets PostgreSQL through the DATABASE_URL environment variable. Applying Django migrations creates the PostgreSQL schema, but does not transfer existing MongoDB data. Test login restoration, role assignment, and cross-tenant/cross-school admin access against a configured PostgreSQL test database.
